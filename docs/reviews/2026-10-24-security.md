## P1: fix before real use

### P1-1. Open redirect after login (VERIFIED)
- `src/app/actions/auth.ts:15`, `:28`
- What's wrong: `next` is accepted when `next.startsWith("/") && !next.startsWith("//")`. Values like `/\evil.example` and `/<TAB>/evil.example` pass that check. Browsers' URL parsing turns both into `https://evil.example/`.
- How I confirmed it in Next 16.4.3:
  - Client: `client/components/router-reducer/reducers/server-action-reducer.js:131` calls `assignLocation(location, …)`, which is `new URL(location, base)`. I tested that in Node: `new URL("/\\evil.example", "https://app/")` gives `https://evil.example/`.
  - `isExternalURL` then triggers `completeHardNavigation` (line ~243). `addBasePath`/`normalizePathTrailingSlash` leave the backslash intact.
  - The no-JS 303 path ends up in the same place.
- Failure scenario: an attacker sends Lauren `https://<app>/login?next=/%5Cevil.example`. She signs in on the real site and lands on a look-alike "session expired, sign in again" page that collects her password.
- Fix: `const u = new URL(next, "http://x"); redirect(u.origin === "http://x" ? u.pathname + u.search : "/")`, or a regex like `^/(?![/\\])[^\s]*$`.

### P1-2. No login rate limiting (VERIFIED; known gap)
- `src/app/actions/auth.ts:12-24`
- What's wrong: unlimited attempts, and each one costs a scrypt computation (about 50 ms CPU). That allows online guessing, and it also burns paid function CPU on Vercel.
- Timing side channel: when the email is unknown, scrypt is skipped (line 22 short-circuits). So response time shows which emails exist (see P2-2).
- Cheapest fix that fits this stack, with no new infra:
  - Add a Neon table `login_attempts(email text, ip text, ok bool, at timestamptz default now())` with an index on `(email, at)`.
  - In `login`, before verifying: count failures for this email OR this IP in the last 15 minutes. If there are 5 or more, return the same generic error.
  - Insert a row on every failure.
  - Get the IP from `(await headers()).get("x-forwarded-for")?.split(",")[0]`. Vercel sets this header.
  - Use a progressive delay rather than a hard lock, so an attacker can't lock Lauren out.
- Zero-code alternative: a Vercel Firewall custom rule that rate-limits `POST /login`. I did not check whether your plan includes it.
- If you'd rather use Redis: Upstash Redis via the Vercel Marketplace with `@upstash/ratelimit`.

### P1-3. CSV import commit is not atomic, and a failure leaves wrong counts (VERIFIED)
- `src/app/actions/import.ts:105-150`
- The commit is a sequence of separate statements, each one its own HTTP request on neon-http:
  1. Insert the `import_batches` row with `insertedCount: 0, skippedCount: 0` (lines 105-114).
  2. Insert transactions in chunks of 200 (lines 117-139).
  3. Update the batch counts (lines 142-145).
  4. Upsert the mapping (lines 147-150).
- Nothing wraps them in a transaction. That's unavoidable on neon-http, whose `session.transaction` throws (`node_modules/drizzle-orm/neon-http/session.js:151-158`).
- Ways it fails partway:
  - (a) A Neon HTTP error, or the function being killed partway through the chunk loop. Some chunks are saved. The batch row stays at "0 added · 0 skipped" in Recent imports (`import/page.tsx:32`).
  - (b) The client shows "safe to try again" (`import-flow.tsx:61`). A retry creates a **second** batch row. Dedupe makes the transactions correct, but the first attempt's rows stay attached to the orphan batch.
  - (c) The planned "Undo an import" (CLAUDE.md #6, delete by `import_batch_id`) on the second batch would leave the first attempt's rows behind.
  - (d) A failure only at the mapping upsert reports an error even though the import fully succeeded. The retry then shows 0 inserted.
- Realistic trigger: one row with |amount| > $21,474,836.47. The `amount_cents` column is `integer`, and `parseAmountToCents` has no bound (`src/lib/money.ts:49`). That happens if a reference or account-number column gets mapped as Amount. The chunk fails with `value out of range for type integer` and the loop aborts.
- Fix options:
  - Give the batch an id up front (`crypto.randomUUID()`) and run everything through `db.batch([...])` on Neon, which runs as one HTTP transaction. Use `db.transaction` on PGlite, which has no `batch`. Put both behind one `runAtomic()` helper.
  - Or switch the prod driver to `drizzle-orm/neon-serverless` (a WebSocket `Pool`). Its `db.transaction` behaves the same as PGlite's.
  - In either case, bound amounts in `parseAmountToCents` to |cents| ≤ 2^31−1.

### P1-4. Prod migrations run without a transaction, unlike dev (VERIFIED)
- `scripts/db.ts:25-27` uses `drizzle-orm/neon-http/migrator`.
- What's wrong: `node_modules/drizzle-orm/neon-http/migrator.js` runs each statement as its own HTTP call, with no transaction. It inserts the `__drizzle_migrations` rows only **after every pending migration has run**.
- PGlite in dev uses `pg-core/dialect.js:60`, which wraps everything in `session.transaction`. So dev never shows this behaviour.
- Failure scenarios:
  - (a) A network blip during the 18-statement `0000_init.sql`. The tables are half-created and nothing is recorded. Re-running fails on `relation "categories" already exists` and needs a manual schema drop.
  - (b) Later, migrations 0001 and 0002 are pending and 0002 fails. 0001 is applied but not recorded. The next run re-applies 0001: it either errors, or, if it is a data migration (e.g. `UPDATE … SET x = x*100`), it **runs twice and corrupts data**.
- Fix: point `scriptDb` migrations at `drizzle-orm/neon-serverless` + `Pool` (Node 22 has a global WebSocket) using `DATABASE_URL_UNPOOLED`. That uses the transactional `dialect.migrate`. At minimum, take a Neon snapshot or branch before each migrate.
- Severity: fine for the first run on an empty DB if it completes. P1 before the second migration.

### P1-5. Server action body limit is 1 MB, but the code and UI promise 5 MB (VERIFIED from docs)
- `next.config.ts` (no `serverActions` key); `src/app/actions/import.ts:11`, `:53`, `:95`.
- What's wrong:
  - The whole CSV text is passed as a server action argument: `previewImport(text, mapping)` and `commitImport(text, …)`.
  - The default limit is 1 MB (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md`, "bodySizeLimit"). The `MAX_BYTES = 5 MB` check and its "5 MB max" message can never trigger.
  - The 5 MB figure also exceeds Vercel's 4.5 MB function request limit. That number comes from your brief; I did not re-check it.
  - `text.length` counts UTF-16 units, not bytes.
  - On top of that, preview re-uploads the full file on every mapping change.
- Failure scenario: a CSV around 1 MB (about 8-10k rows, e.g. multi-year history or the planned QuickBooks import, #8) is rejected. The client's `catch` shows "Couldn't read that file. Is it a CSV export?" (`import-flow.tsx:26`), which is misleading.
- Fix: set `experimental: { serverActions: { bodySizeLimit: "4mb" } }`, and set `MAX_BYTES` to about 3.5 MB measured with `new TextEncoder().encode(text).length`. Also check `file.size` in the client before upload and show a clear "too big, split by date range" message.

## P2: nice to have / hardening

1. **No way to revoke a session** (VERIFIED). `src/lib/auth.ts:23-25`, `src/lib/session-token.ts:7`.
   - Logout only deletes the cookie. The JWT stays valid for 30 days.
   - Resetting a password with `user:add` does not invalidate existing sessions.
   - Deleting a user does not revoke their token. `getSession` never checks that the user exists, and later `createdBy` FK inserts then fail with a 500.
   - Scenario: a lost or stolen phone keeps a month of access to the books.
   - Fix: put a `session_version` int on `users` and in the JWT, and check it in `requireUser()` (the proxy can stay stateless). Emergency runbook until then: rotate `SESSION_SECRET` in Vercel and redeploy, which logs out everyone.
2. **Login timing reveals which emails exist** (VERIFIED). `src/app/actions/auth.ts:22`. No scrypt runs when the user is missing. Fix: run `verifyPassword(password, DUMMY_HASH)` when the user is not found.
3. **scrypt cost is Node's default** (VERIFIED). `src/lib/password.ts:10`.
   - N=16384, r=8, p=1. OWASP's current minimum is N=2^17.
   - The hash format `scrypt$salt$hash` doesn't record the parameters, so raising the cost later needs a format change.
   - Fix: `scrypt$N$r$p$salt$hash`, with `{N: 2**17, r: 8, p: 1, maxmem: 256*1024*1024}`.
4. **A malformed stored hash accepts any password** (VERIFIED by running it in Node). `src/lib/password.ts:17-19`.
   - With `hashHex` = `"zz"` or `"x"`, `Buffer.from(hex)` is empty, so `scrypt(…, 0)` returns an empty buffer and `timingSafeEqual(empty, empty)` is `true`.
   - Only reachable if a `users.password_hash` value is corrupted or written by hand.
   - Fix: `if (expected.length !== KEY_LEN) return false`.
5. **The proxy matcher skips some app paths** (matcher VERIFIED by regex simulation; render effect SUSPECTED). `src/proxy.ts:16`.
   - The proxy doesn't run for any path ending in `.png/.svg/.ico/.webmanifest`, or starting with `login`, `icon`, `apple-icon` or `manifest` (e.g. `/loginx`, `/iconography`).
   - `/stylists/x.png` and `/transactions/x.svg` therefore reach the dynamic pages unauthenticated. Those 404 without showing any record. But the `(app)` layout's `InboxBadge` (`src/app/(app)/layout.tsx:20-21`) still runs, so the uncategorized count leaks, and the stylists page runs a full `getStylists()` query (`stylists/[id]/page.tsx:24`).
   - There is no `public/` dir, so the extension exclusion buys nothing.
   - Fix: anchor the exclusions, e.g. `/((?!login$|login/|_next/static|_next/image|favicon\\.ico$|icon|apple-icon|manifest)(?!.*\\.(?:png|svg|ico|webmanifest)$)…)`, or just limit them to root-level files. Server Actions don't depend on the proxy (see "fine" list).
6. **Server action arguments aren't validated at runtime** (VERIFIED).
   - `src/app/actions/import.ts:51`, `:93`: `text`, `mapping`, `filename` are TypeScript-typed only. A tampered payload can store an arbitrary JSON blob as the saved BMO mapping (line 149), which is then fed back into every future preview. A non-string `filename` or `text` crashes with a 500 (`filename.slice`, `text.replace`).
   - `z.uuid().parse(...)` throws (500) instead of returning, in `settings.ts:67`, `:94`, `stylists.ts:66`, `transactions.ts:93`.
   - `settings.ts:26`: a missing `totalChairs` field silently becomes 0.
   - Both users are trusted, so these are crash or garbage risks, not breaches.
   - Fix: zod schemas for the import arguments (`z.string().max()`, a `CsvMapping` object schema, `z.string().max(200)`), and `safeParse` everywhere.
7. **Unbounded `inArray`** (VERIFIED). `src/app/actions/transactions.ts:158`. A single (category, stylist) group with more than 65,534 ids exceeds Postgres's bind-parameter limit. Only plausible after a huge uncategorized history import. Fix: chunk `g.ids` by 5,000.
8. **`getDb()` caches a rejected promise** (VERIFIED). `src/db/index.ts:17`. If the first call throws (e.g. env var missing or a transient import error), that function instance keeps failing until it's recycled. Fix: `dbPromise = createDb().catch(e => { dbPromise = null; throw e; })`.
9. **Type cast hides driver differences** (VERIFIED). `src/db/index.ts:34`, `scripts/db.ts:19`.
   - PGlite is cast to `NeonHttpDatabase`, so the two drivers fail in opposite directions. `db.transaction(...)` type-checks and works in dev but throws in prod (`neon-http/session.js:151-158`). `db.batch(...)` type-checks but doesn't exist on PGlite.
   - Neither is used today (grep VERIFIED). Any atomic-import fix (P1-3) has to handle both.
   - Fix: a small `runAtomic` wrapper plus a lint ban on `db.transaction` and `db.batch` outside it.
10. **`.env.example` is missing** (VERIFIED).
    - README step `cp .env.example .env` and the `scripts/db.ts:10` error message both refer to it, but it isn't in git or on disk.
    - `.gitignore` has `.env*`, so even a new one would be ignored unless you add `!.env.example`.
    - Fix: add it with `DATABASE_URL=`, `SESSION_SECRET=` and the generator command (`openssl rand -base64 48`).
11. **`db:seed` is not safe to re-run after renames** (VERIFIED). `scripts/seed.ts:9-17` matches categories by **name**.
    - After Lauren renames a default category, re-running seed re-adds the old one.
    - After she renames "Booth Rent", seed crashes on the `system_key` unique constraint (`renameCategory` allows renaming system categories, `settings.ts:53-62`).
    - Fix: key the seed on `systemKey`, or seed only when the categories table is empty.
12. **`user:add` takes the password on the command line** (VERIFIED). `scripts/add-user.ts:10`. It ends up in `~/.zsh_history` and is visible in `ps`. Fix: read it from a hidden prompt or `stdin`.
13. **No security headers** (VERIFIED, `next.config.ts`).
    - There is no `headers()`: no `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy` or `nosniff`.
    - Clickjacking is mostly blunted by the `SameSite=Lax` cookie, which isn't sent in cross-site iframes.
    - Fix: add a `headers()` block with `X-Frame-Options: DENY` and `Referrer-Policy: same-origin`. Optionally name the cookie `__Host-lm_session`.
14. **A missing or short `SESSION_SECRET` fails closed but silently** (VERIFIED). `src/lib/session-token.ts:13`.
    - In the proxy, `verify` swallows the throw, so everyone is redirected to `/login`.
    - `login` then throws in `createSession`, and the user gets a generic error page.
    - That's safe, but hard to diagnose on the first deploy. Fix: check env vars once at startup (`instrumentation.ts`) and log a clear message.
15. **Preview deployments may expose real data** (SUSPECTED; Vercel/Neon config, not code).
    - If the Neon integration creates a database branch per preview, preview URLs serve a copy of production data.
    - Fix: keep Vercel Deployment Protection on for previews, and use a different `SESSION_SECRET` for Preview vs Production.
16. **PGlite is bundled in production** (SUSPECTED). `next.config.ts:7`, `src/db/index.ts:30`. `serverExternalPackages` plus a dynamic import means file tracing probably copies PGlite and its WASM into the prod function. It's never loaded, so it's not a blocker. Just bigger cold-start bundles.

## Answers to the six questions

**Q1. Session and cookie** (VERIFIED)
- Signing: HS256 via `jose`, with `algorithms: ["HS256"]` pinned on verify, so there's no algorithm confusion.
- Secret: at least 32 characters, enforced at use time; it fails closed (P2-14).
- Expiry: `exp` is 30 days and the cookie `maxAge` matches. There's no sliding refresh.
- Cookie flags: `httpOnly: true`, `secure` when `NODE_ENV==="production"` (true on Vercel, Preview included), `sameSite: "lax"`, `path: "/"`.
- Logout: only deletes the cookie; nothing is revoked server-side (P2-1).
- Password compare: `timingSafeEqual` is used, with a length guard (but see P2-4).
- scrypt: Node defaults N=16384, r=8, p=1, a 16-byte salt and a 64-byte key (P2-3).

**Q2. Proxy coverage** (VERIFIED)
- The proxy runs on everything except `/login*`, `/_next/static`, `/_next/image`, `/favicon.ico`, `/icon*`, `/apple-icon*`, `/manifest*`, and any path ending in `.png/.svg/.ico/.webmanifest`.
- `/reports/export` is covered by the proxy, and the route also returns 401 itself (`route.ts:15`).
- The only app routes reachable unauthenticated are the extension-suffix dynamic paths (P2-5). They leak the Inbox count and nothing else.
- The docs (`proxy.md:249-251`) say Server Actions posted to an excluded path (e.g. `/login`) skip the proxy entirely. So the per-action checks are the real boundary, and they hold.

**Q3. Actions and routes missing auth** (VERIFIED)
- None missing. These all call `requireUser()` on their first line, before any DB call: `previewImport`, `commitImport`, `saveBusinessSettings`, `addCategory`, `renameCategory`, `toggleCategoryArchived`, `addRule`, `deleteRule`, `saveStylist`, `deleteStylist`, `createTransaction`, `updateTransaction`, `deleteTransaction`, `categorizeTransaction`, `applyRulesToUncategorized`.
- `login` and `logout` correctly have no check.
- The helpers that do DB work (`existingHashes`, `setSetting`, `applyRules`) are not exported, so they are not actions.
- There are no inline `"use server"` closures.

- Neon v1 `neon()` compatibility: drizzle 0.45.4 calls `client.query ?? client` (`neon-http/session.js:24`), so it's v1-compatible.
- Is the CSV commit atomic? No (P1-3).
- Bind-parameter limit:
  - Insert chunks are 200 rows × 9 bound params (date, amountCents, description, categoryId, stylistId, source, importBatchId, dedupeHash, createdBy) = 1,800. Drizzle writes `default` for undefined columns.
  - Hash lookups use 500 params.
  - Both are far under 65,535. The request-size limit (P1-5) caps a CSV long before params matter. The only unbounded list is P2-7.
  - If anyone moves the commit to a single statement, cap it at about 7,000 rows (65,535 / 9).

**Q5. Deploy blockers**
- Env vars needed: `DATABASE_URL` (set by the Neon integration) and `SESSION_SECRET` (32+ random characters; set it in Vercel for Production and Preview). `NODE_ENV` is automatic. The closure-encryption key isn't needed on Vercel.
- Migrations: `npm run db:migrate` from a laptop with Neon's `DATABASE_URL`. It works on an empty DB if the run completes, but it isn't transactional (P1-4). Snapshot first.
- Local disk: none at runtime. PGlite is used only when the URL starts with `pglite:`, and the CSV comes in as text.
- Body size: the 1 MB action limit is the effective cap, below Vercel's 4.5 MB (P1-5). `next.config.ts` has no `serverActions` key.
- Proxy body buffering: proxies buffer request bodies up to 10 MB by default (`proxyClientMaxBodySize`), which isn't a constraint here.
- Function duration (SUSPECTED, low risk): commit makes about (rows/500 + rows/200 + 5) sequential HTTP round-trips. That's about 75 for 10k rows, a few seconds. Keep the Vercel function region next to the Neon region.
- Docs gap: `.env.example` is missing (P2-10).

**Q6. Brute force**: Confirmed there is no rate limiting. Cheapest fix: the Postgres attempts table in P1-2.

## Things that are fine (checked)
- **Auth before side effects:** every exported action calls `requireUser()` first; `redirect()` throws, so nothing after it runs. The export route checks `getSession()` before any read.
- **CSRF:** Next checks Origin against Host on every Server Action (`serverActions.md`, "allowedOrigins"), and there's no `allowedOrigins` override. GET `/reports/export` has no side effects.
- **JWT handling:** the algorithm is pinned; `userId` and `name` are type-checked on verify; a missing or short secret makes verification return null (fails closed).
- **XSS:** no `dangerouslySetInnerHTML`, `eval` or `innerHTML` anywhere (grep), and React escapes bank descriptions. Hrefs are built from UUIDs and validated month keys.
- **CSV export:** `safeText` neutralises formula injection on every text column. The `Content-Disposition` filename uses only validated ISO dates. `Cache-Control: no-store` is set.
- **SQL:** all queries go through the Drizzle builder, and the only raw SQL is a constant `count(*)::int`.
- **Caching:** there is no `"use cache"`, `unstable_cache` or `cacheTag` anywhere, so per-user data can't be cached across users. Data reads call `connection()`.
- **Import dedupe:** the unique `dedupe_hash` index plus `onConflictDoNothing` makes double-submits and retries safe for the transaction rows themselves.
- **Route params:** `/transactions/[id]` validates the id shape before querying; `/stylists/[id]` does an in-memory lookup and returns `notFound()`.
- **Report ranges:** `resolveRange` validates ISO dates and `from <= to`, and falls back to YTD.
- **Demo data:** `demo-data.ts` refuses anything that isn't a PGlite URL.
- **Repo and history:** no secrets in the git history (both commits checked); `.pglite` and `.env*` are gitignored; `robots: noindex` is set in the root layout.
- **Migration timestamp:** the journal's `when` (2026-10-24T15:25Z) is not in the future, so the next generated migration won't be skipped.
