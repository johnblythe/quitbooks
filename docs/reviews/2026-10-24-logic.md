# QuitBooks logic audit: money, dates, CSV import, categorization, metrics

Scope: read-only review of `src/lib/{money,dates,csv,categorize,metrics,report-range,data}.ts`, the import/transaction/settings/stylist actions, the dashboard, reports and export route, the Inbox and the import flow.

Evidence:
- `repro.ts` (session scratchpad, not committed) was run with `tsx`. It imports the real `src/lib/*.ts`. `suggestPattern` and `safeText` are copied verbatim because they aren't exported. Section numbers below ("§n") refer to its output.
- `neon-date.mjs` (session scratchpad, not committed) was run with `TZ=<zone> node`.


Severity: P0 = wrong numbers or silent data loss · P1 = fix before real use · P2 = nice to have.

---

## P0

### P0-1. A manual entry and the same bank row imported later are both counted
- **Where:** `src/app/actions/transactions.ts:61-71` inserts manual rows with no `dedupeHash`. `src/app/actions/import.ts:34-48` and `:101-102` (`existingHashes`) compare only `dedupe_hash`. `schema.ts:79,88`.
- **What's wrong:** import dedupe only sees rows that came from a CSV. A Zelle that Lauren enters by hand when it arrives (+$250, 10/01, "Jane rent") will import again from the month-end BMO CSV as "ZELLE FROM JANE DOE +250.00 10/01". The preview counts it as **new**, not "Already imported". Booth rent income for that payment is counted twice in the P&L and the dashboard, and the stylist shows as "Ahead".
- **Failing input → wrong output:** a manual +$250.00 on 2026-10-01, then a CSV containing `10/01/2026,ZELLE FROM JANE DOE,250.00`. Result: two rows, $500 of income.
- **Fix:** in `previewImport`, flag CSV rows that match a `source='manual'` transaction with the same amount within ±3 days as "possible duplicate", unchecked by default. Optionally let the user link the import to the manual row by writing the hash onto it.
- **Status:** VERIFIED-BY-READING. Needs a DB to run end to end. Manual inserts never set `dedupeHash`, and nothing else in the import path reads manual rows.

## P1

### P1-1. Stylist matching is a bare substring match, ignores active dates, and beats every rule. Transfers and other deposits become Booth Rent income.
- **Where:** `src/lib/categorize.ts:36-44` (`stylistTerms` falls back to the name when it's ≥3 chars), `:47-60` (`desc.includes(term)`, no word boundary, no `startDate`/`endDate` check even though the type carries them), `:85-88` (stylist match runs before rules).
- **What's wrong:** a stylist named "Ann" with no match text claims every deposit containing "ANN": JOANNE, ANNUAL, SHANNON, CHANNEL. "Eve" would match REVENUE and EVENT; "Sam" would match SAMS CLUB and SAMSUNG; "Lee" matches FLEET and COLLEEN. An owner contribution or savings transfer that should be a transfer (excluded from P&L) becomes Booth Rent **income**, and the stylist's rent shows as collected. A rule can't override it, because stylist matching runs first. A stylist who has left (end date in the past) still matches. These rows never reach the Inbox, so nobody reviews them.
- **Failing input → wrong output (§12):** stylist `Ann` (no match text), rule `TRANSFER FROM → Owner Contribution (in)`. `+$250 "ONLINE TRANSFER FROM SHANNON BLYTHE SAVINGS"` → `{categoryId: booth, stylistId: ann}`. `"ANNUAL REWARDS CREDIT"` → Booth Rent from Ann. Stylist `Lee` with end date 2026-03-31: `"SQUARE INC DEPOSIT FLEET"` on 2026-10-01 → Booth Rent from Lee.
- **Fix:** match on whole words (`\bTERM\b` after escaping). Only match stylists active on `tx.date`. Let an explicit rule (or a rule with a "beats stylist" priority) win. Consider requiring ≥2 words when falling back to the name.
- **Status:** REPRODUCED (`repro.ts` §12).

### P1-2. Changing the column mapping changes every dedupe hash, so an overlapping re-import doubles rows
- **Where:** `src/lib/csv.ts:165-170,179` builds the hash from the description *after* the memo column is appended, and from the amount *after* `invertSign`. The mapping can be edited in `import/import-flow.tsx:141,148` and is re-saved on every commit (`import.ts:147-150`).
- **What's wrong:** the likeliest trigger is the PRD's own open question. After the first import, the user finds that Zelle sender names are in a separate column and adds it as "Extra details". Every overlapping row from the next export now gets a new hash, the preview shows it as **new**, and it is inserted a second time. Toggling "money out as positive", or picking a different description column, does the same.
- **Failing input → wrong output (§7):** import `Date,Description,Memo,Amount` with mapping {description: Description, no memo}, then re-import the same file with the memo column set. 2 of 2 rows are treated as new, where 0 was expected. Toggling `invertSign` gives the same 2/2.
- **Fix:** hash the raw source fields (date column value, raw amount cell(s), raw description column only, plus the occurrence index) independent of memo and sign options. At minimum, warn when the mapping differs from the saved one and the preview has 0 "already imported" rows inside a date range that's already in the DB.
- **Status:** REPRODUCED (§7).

### P1-3. "Remember for similar transactions" often creates a rule that can't match anything, including the transaction it came from
- **Where:** `src/app/(app)/inbox/page.tsx:11-18` (`suggestPattern` drops words that contain digits and 1-char words, then joins the rest with spaces), `src/app/actions/transactions.ts:122-125`.
- **What's wrong:** the suggested pattern isn't a contiguous substring of the description whenever a dropped word sits between kept ones. The rule is saved and `applyRules` runs, but it never matches, so the user thinks the app learned and the Inbox keeps filling.
- **Failing input → wrong output (§13):** `"POS 1234 SALLY BEAUTY INDIANAPOLIS"` → pattern `"POS SALLY BEAUTY INDIANAPOLIS"` → doesn't match its own transaction. Same for `"ZELLE 10/01 FROM JANE DOE"` → `"ZELLE FROM JANE DOE"` (no match), and `"DEBIT CARD PURCHASE - SALLY BEAUTY #12"` → `"DEBIT CARD PURCHASE SALLY"` (no match). Separately, the suggestion can be too broad: `"ZELLE PAYMENT FROM JANE"` also matches `"ZELLE PAYMENT FROM JANET LEE"`.
- **Fix:** suggest the longest contiguous run of digit-free words. Before saving, check `matchRule(thisTx, [newRule])` and refuse (or warn) if it fails. Show the count of other Inbox items the rule would catch (already on the roadmap).
- **Status:** REPRODUCED (§13, with `suggestPattern` copied verbatim).

### P1-4. A remembered Booth Rent rule never tags the stylist, so their rent shows as unpaid
- **Where:** `src/app/actions/transactions.ts:123` (rule saves `{pattern, categoryId, direction}` only), `src/lib/categorize.ts:90` (a rule match returns `stylistId: null`), `src/lib/metrics.ts:191-193` (collected requires a `stylistId`).
- **What's wrong:** Zelle payments land in the Inbox exactly when stylist matching fails. The user picks Booth Rent + Jane and ticks Remember. Jane's later payments become Booth Rent with no stylist, so her row on the dashboard shows "Due/Short" every month while the P&L total is right.
- **Failing input → wrong output (§13):** rule `"ZELLE PAYMENT FROM JANE" → booth`. `categorize(+$250 "ZELLE PAYMENT FROM JANE DOE")` → `{categoryId: "booth", stylistId: null}`.
- **Fix:** when the category is Booth Rent and a stylist is picked, append the pattern to that stylist's `matchText` instead of (or as well as) creating a rule. Alternatively, add an optional `stylistId` to rules.
- **Status:** REPRODUCED (§13).

### P1-5. CSV rows that fail to parse are dropped at commit with only a collapsed warning, and the result screen doesn't mention them
- **Where:** `src/lib/csv.ts:148-164` (bad rows go to `errors`), `src/app/actions/import.ts:97-102,141` (only `rows` are committed; `skipped` counts duplicates only), `src/app/(app)/import/import-flow.tsx:165-176` (errors sit inside a closed `<details>`), `:66-74` (the success card shows inserted and duplicate counts only), `:202-203` (the button stays enabled).
- **What's wrong:** an unquoted comma in a description, an amount format like `45.00 CR`, a date with a time, or a blank amount cell all lose the row. The user sees "Imported 182 transactions" and moves on, and the P&L is missing those rows.
- **Failing input → wrong output (§9, §5):** `10/01/2026,SALLY BEAUTY, INC,-45.00` → no row; the error is listed twice (line 2). §2: `10/01/2026 12:00:00 AM` → `null`, so the row is dropped.
- **Fix:** show the error count prominently next to the Import button and in the result ("3 rows couldn't be read and were NOT imported"). Consider requiring an acknowledgement checkbox when errors > 0.
- **Status:** REPRODUCED for the parse drop (§9). The UI behaviour is VERIFIED-BY-READING.

## P2

### CSV and import
- **P2-1. A preamble line containing "date" and a comma is taken as the header, which blocks the import.** `src/lib/csv.ts:122-127`. `"Account: BMO ****1234, Statement date: 10/24/2026"`, or even `"Last updated 10/24/2026, 3:00 PM"` ("upDATEd"), becomes the header. Result: 0 rows, the "map manually" dropdowns only offer the preamble's fields, and there's no way round it in the app. Fix: choose the first line whose cells exactly match a known date header, or the first line where `detectMapping` succeeds. REPRODUCED (§8). This depends on BMO's real format, so check it with the fixture (roadmap #1).
- **P2-2. In split mode a negative credit (a reversal) is recorded as money in.** `csv.ts:107` `Math.abs(credit) - Math.abs(debit)`. `Credit = -200.00 "RETURNED DEPOSIT"` → +20000, where −20000 was expected. Fix: only `abs()` the debit; treat a signed credit as-is, or flag the row. REPRODUCED (§10). SUSPECTED relevance: it depends on how BMO writes reversals.
- **P2-3. Unsigned amounts with a Debit/Credit or Type indicator column aren't supported.** `csv.ts:64-83`. `detectMapping([Date,Description,Amount,Debit/Credit])` → single mode, so every row is positive. `RENT 1500.00 DEBIT` → +150000. The preview shows everything green, so it's not silent. Fix: add an optional `directionColumn` + debit token. REPRODUCED (§10). SUSPECTED relevance (BMO format).
- **P2-4. Date formats with a time, or in `YYYYMMDD` form, are rejected.** `dates.ts:29` is anchored with `$`. `"10/01/2026 12:00:00 AM"` and `"20261001"` → `null` (the row errors, which feeds P1-5). Fix: allow a trailing time and add `^\d{8}$`. REPRODUCED (§2).
- **P2-5. A comma used as a decimal separator gives a value 100× too large.** `money.ts:38` strips every comma. `"45,50"` → 455000 ($4,550.00) instead of `null`. `"1,23.45"` → 12345. This matters most for manual entry and the opening balance. Fix: reject a comma that isn't followed by exactly 3 digits. REPRODUCED (§1).
- **P2-6. Error line numbers drift when blank lines appear mid-file.** `csv.ts:149` uses `idx` after Papa's `skipEmptyLines`. A bad row on line 5 is reported as line 3. REPRODUCED (§11).
- **P2-7. Deleting an imported transaction removes its hash, so the next overlapping import restores it.** `transactions.ts:96`. Someone who deletes a "duplicate" by hand will see it come back. Fix: soft-delete, or keep a tombstone of the hash. VERIFIED-BY-READING.
- **P2-8. `commitImport` isn't atomic.** `import.ts:105-145`. A failure part-way leaves a batch with `insertedCount: 0` and some rows inserted. A retry dedupes correctly; only the batch counts end up wrong, which will matter for "Undo import". VERIFIED-BY-READING.
- **P2-9. Hash stability depends on BMO not changing a row's date or description between pending and posted.** If BMO exports pending rows, the same transaction shows up again once it posts. SUSPECTED; check against a real export.
- **P2-10. `parseAmountToCents(number)` goes through floats.** `money.ts:24` `Math.round(input*100)`: `1.005` → 100 and `0.285` → 28, while the string path is correct. There are no callers today (every call site passes a string). Fix: delete the number branch, or route it through `toString()`. REPRODUCED (§1).
- **P2-11. Neon's DATE parser returns local midnight, and drizzle converts it with `toISOString()`.** `src/db/index.ts:37`, `drizzle-orm/pg-core/columns/date.js:46-49`. Under `TZ=Asia/Tokyo` (or any zone east of UTC), `2026-10-01` reads back as `2026-09-30`. It's correct on Vercel (UTC) and on US machines. Fix: `types.setTypeParser(1082, v => v)` on the Neon client, or never set TZ east of UTC. REPRODUCED (`neon-date.mjs`).

### Categorization
- **P2-12. Equal-priority rules with equal-length patterns apply in arbitrary order.** `data.ts:185` (`select().from(rules)` with no ORDER BY) plus `categorize.ts:65-67`. There's no UI to set priority, so every rule is priority 100. `"AMAZON MKTPLC"` with rules AMAZON→Supplies and MKTPLC→Cleaning gives either result depending on row order. Fix: break ties on `createdAt`/`id`. REPRODUCED (§14).
- **P2-13. Categorizing a manual entry in the Inbox wipes its stylist.** `inbox/page.tsx:86` (`defaultValue=""`) and `transactions.ts:114-120`. A manual entry saved with a stylist and no category arrives in the Inbox with `stylistId` set, and saving it there sets `stylistId` to null. Fix: `defaultValue={tx.stylistId ?? ""}`. VERIFIED-BY-READING.

### Metrics and dashboard
- **P2-14. Chairs filled counts anyone active on any day of the month.** `metrics.ts:209-216`. With 1 chair, a stylist leaving Oct 3 and one starting Oct 20 gives `{filled: 2, total: 1}`. The card shows "2 / 1" and "Every chair is rented". Someone starting later this month also counts as filled today. Fix: for the current month, count stylists active on today's date; for past months, count those active on the last day. REPRODUCED (§15).
- **P2-15. Monthly rent isn't pro-rated, or skipped, for a mid-month start or end.** `metrics.ts:150-152`. A stylist starting Oct 28 is expected to pay the full $1,000 for October, and one whose end date is Nov 1 owes a full November, so both get "Short" flags. This is outside the accepted weekly/biweekly caveat. REPRODUCED (§15).
- **P2-16. Rent status is per month with no carry-forward, so missed rent disappears the next month.** `metrics.ts:183-207`. If September rent is paid Oct 1, September shows "Short $1,000" and October shows "Paid", although one payment is still missing. A stylist who is consistently one payment behind looks "Paid" on the default (current-month) view. Fix: show a running balance since the start date alongside the month view. REPRODUCED (§15). Whether to fix is a product call.
- **P2-17. Runway's "monthly expenses" leave out owner draws.** `metrics.ts:230-236`, fed by P&L expenses at `page.tsx:55,60`. Window: the 3 complete months before the selected month, ignoring zero-expense months. Owner Draw is a transfer, so it isn't counted. With $1k/mo expenses, $4k/mo draws and a $10k balance, runway shows 10 months while cash actually lasts about 2. The label "covers this long at recent spending" (`page.tsx:203`) overstates it. Fix: either base runway on cash outflows (all negative amounts minus inter-account transfers) or reword the label. REPRODUCED (§15). Product call.
- **P2-18. "vs 3-mo avg" and "vs last month" compare a partial month with full months, and new installs divide by 3 anyway.** `page.tsx:215-229` (avg = sum/`priorMonths.length`, always 3) and `:107`. Early in the month every category shows something like −80%. With only one prior month of data, avg is ⅓ of that month, so categories show ~+200% in red. Fix: pro-rate the current month or label it "so far". Divide by the number of months that actually have data. VERIFIED-BY-READING.

### Reports and export
- **P2-19. The summary CSV carries no uncategorized warning, and the detail CSV doesn't add up to the P&L net.** `reports/export/route.ts:35-45` and `:22-34`. The summary has "Uncategorized" lines but no count. The detail export includes transfers (Type=transfer), so summing Amount ≠ net. That's by design but not explained in the file. Fix: add a note row or footer. VERIFIED-BY-READING.
- **P2-20. A user category named "Uncategorized" would get the warning style.** `reports/page.tsx:118` checks `l.name === "Uncategorized"` instead of the sentinel IDs. VERIFIED-BY-READING.

## Checked and fine
- **`parseAmountToCents` string path** uses integer maths only. An exhaustive round-trip of every value from $0.00 to $10,000.00, both signs, had 0 mismatches. `0.29`→29, `19.99`→1999, `1.005`→101 (half-up), `0.295`→30, `$1,234.56`, `(45.00)`, `-45.00`, `45.00-`, `$-45.00`, `-$45.00`, `($45.00)` and `.5` are all correct. Junk (`1e3`, unicode minus, `45.00 CR`) returns `null` rather than a wrong number.
- **Export `dollars()`** (`(c/100).toFixed(2)`) round-trips exactly for −$20k..$20k.
- **Dates:** `parseBankDate` handles MM/DD/YYYY, M/D/YY, YYYY-MM-DD, MM-DD-YYYY and ISO-with-time, and rejects impossible dates (02/29/2025, month 13).
- **CSV basics:** the BOM is a literal U+FEFF in the regex at `csv.ts:120` (checked with xxd). CRLF, quoted fields with commas, preamble plus blank lines, and split mode with blank debit/credit cells all parse. A row with both cells blank is an error, not $0.
- **Dedupe with the occurrence counter:** two identical same-day Zelles in one file are both kept, and an overlapping re-import dedupes both. A later export with a third identical row adds exactly 1. The result doesn't depend on row order (newest-first works) or on whitespace, case, date format or amount format. Editing an imported transaction keeps its hash. Several NULL hashes are allowed (plain unique index, `drizzle/0000_init.sql:92`). `onConflictDoNothing` covers a double submit.
- **Time zones:** `todayIso()` uses `America/Indiana/Indianapolis` via Intl, independent of server TZ. It returns 10-24 until 04:00Z (local midnight EDT) and handles the DST changeover (§3). Server components use `requestToday()`. The export route uses `todayIso()` inside a dynamic handler, which is fine. `formatDate`/`formatMonth`/`addDays` are all UTC-based, so nothing drifts. `resolveMonth` blocks future months.
- **Report presets:** This month, last month (January rolls back to December of the prior year), quarter (Mar 31 and Dec 31 boundaries), YTD and last year are all correct. `from > to` falls back to YTD.
- **`computePnl`:** transfers are excluded. Uncategorized rows stay in the totals as separate "Uncategorized" in/out lines and are counted, so they don't silently vanish. Refunds net within their category. The dashboard, reports and export all load archived categories (`includeArchived: true`), so archived history still counts.
- **Summary CSV reconciles with the on-screen P&L:** both run the same `computePnl` over the same inputs.
- **CSV injection guard** covers `= + - @ \t \r` on every free-text column (Description, Category, Stylist, Note, summary category names). Date, Type and Amount can't carry a formula.
- **`expectedRentForMonth`:** the weekly/biweekly jump-ahead is correct, and end dates and active-in-month checks are inclusive.
- **`runwayMonths`:** no divide by zero (returns null), a negative balance gives 0, and zero-expense months are excluded (the conservative choice).
- **`currentBalance`** includes transactions dated on `asOf`, which matches the "As of the start of" label (`settings/business-form.tsx:30`). The dashboard's fetch window covers balance, the 6-month bars and the 3 prior months.
- **Rule matching** normalises case and whitespace on both sides. The direction filter is correct, with $0 excluded from both directions.
- **The Neon driver on Vercel** (UTC) returns correct `YYYY-MM-DD` strings (see P2-11 for the caveat).
